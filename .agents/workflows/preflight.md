# プリフライトチェック ワークフロー

**対象**: Lead（Antigravity）・GLM 両方に適用

特定の操作（PR作成・デプロイ・マージ等）の前に、自動的にチェックリストと検証を実行するパターン。
問題を早期検出し、壊れた状態でのpushやリリースを防ぐ。

---

## チェックの種類と担当

| チェック種別 | 担当 | タイミング |
|---|---|---|
| コード品質（型・lint） | Lead | コミット前 |
| テスト通過確認 | Lead | PR作成前 |
| セキュリティスキャン | glm-46f | PR作成前・マージ前 |
| コードレビュー（批評） | glm-46e | PR作成前 |
| 破壊的操作ガード | Hooks（自動） | 常時 |

---

## パターン1: コミット前チェック（Lead実行）

コミット前に必ず実行する最小チェックセット。

```
[Lead] 以下を順に実行：

① 型チェック
  npm run typecheck  / tsc --noEmit  / mypy src/

② Lintチェック
  npm run lint  / ruff check .  / eslint src/

③ ユニットテスト
  npm test  / pytest  / go test ./...

④ チェック結果の確認
  すべて PASS → コミット続行
  いずれか FAIL → 原因を修正してから再実行（スキップ禁止）
```

**原則: テストが通らない状態でコミットしない。`--no-verify` は使わない。**

---

## パターン2: PR作成前チェック（Lead + GLM並列）

PRを出す前に、Lead とGLM が並列でチェックを実行する。

```
[Lead] パターン1（コミット前チェック）が通っていることを確認

[並列実行]
  [Lead]    ビルド確認（npm run build / go build）
  [glm-46e] コードレビュー（批評・改善提案）
  [glm-46f] セキュリティスキャン

[Lead] 全結果を集約：
  - ビルド FAIL → 修正してから再実行
  - glm-46e の指摘 → 重大なもの（バグ・型エラー）は修正、軽微なものはコメントに記録
  - glm-46f の HIGH/MEDIUM リスク → 必ず修正してから PR を出す

[Lead] PR作成
```

### glm-46e へのプロンプト（PRレビュー用）

```
あなたはシニアTypeScriptエンジニアです。PRに含まれる変更をレビューしてください。

【確認観点】
1. ロジックエラー・バグの可能性
2. 型安全性（anyの使用・型推論の漏れ）
3. テストの網羅性（カバーされていないケース）
4. コードの可読性・保守性
5. 既存コードとの整合性・依存関係

【変更コード】
<diff または変更ファイルの内容をここに貼る>

【関連コンテキスト】
<型定義・インターフェース・テストコードをここに貼る>

問題点と改善提案を重大度（CRITICAL/WARNING/INFO）付きで箇条書きで出力してください。
CRITICALがない場合は「レビューOK」と明記してください。
```

### glm-46f へのプロンプト（セキュリティスキャン用）

```
あなたはシニアセキュリティエンジニアです。PRに含まれる変更のセキュリティリスクを検査してください。

【確認観点】
1. インジェクション脆弱性（SQL・XSS・コマンドインジェクション）
2. 認証・認可の欠陥（権限チェック漏れ・セッション管理）
3. ハードコードされたシークレット・APIキー
4. 安全でない外部入力の処理（バリデーション不足）
5. 機密データの不適切な露出（ログ出力・エラーメッセージ）
6. 依存ライブラリの既知脆弱性

【変更コード】
<diff または変更ファイルの内容をここに貼る>

セキュリティリスクを深刻度（HIGH/MEDIUM/LOW）付きで箇条書きで出力してください。
問題がない場合は「セキュリティ問題なし」と明記してください。
```

## パターン3: デプロイ前チェック（本番リリース前）

本番環境へのデプロイ前に実施する包括的なチェック。

```
[Lead] 以下を順に実行：

① 全テスト実行（ユニット + インテグレーション）
② ビルド確認（本番ビルド設定で）
③ 環境変数の確認（必須の env が設定されているか）
④ マイグレーション確認（DBスキーマ変更がある場合）

[並列実行]
  [glm-46e] 変更箇所のロジックレビュー
  [glm-46f] 本番コードのセキュリティスキャン

[Lead] 全チェックがOKであることを確認してからデプロイ承認をユーザーに求める
```

**原則: デプロイはユーザーの明示的な承認なしに実行しない。**

---

## パターン4: GLM生成コードの受け入れチェック

GLMが生成したコードをファイルに書き込む前の検証。

```
[Lead] GLMから生成コードを受け取る

① 構文チェック（手動レビュー or エディタで確認）
  - 明らかな構文エラーがないか
  - インポートが正しいか
  - 型定義が整合しているか

② セキュリティチェック（目視）
  - ハードコードされたシークレットがないか
  - 安全でない関数（eval、exec等）を使っていないか
  - 入力バリデーションが適切か

③ [glm-46f] 自動セキュリティスキャン（認証・決済・データ変更コードは必須）

④ 問題なければファイルに書き込む
   問題があれば → GLMに修正指示を出して再生成
```

**IMPORTANT: 認証・決済・データ変更のコードはユーザーが手動レビューする。**

## Hooks による自動プリフライト

`.claude/settings.json` で特定のツール実行前に自動チェックを走らせる：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{
          "type": "command",
          "command": "echo '$CLAUDE_TOOL_INPUT' | grep -qE '(git push|npm publish|docker push)' && echo '[PREFLIGHT] push/publish操作を検出。テストが通っているか確認してください。' || exit 0"
        }]
      }
    ]
  }
}
```

## チェック結果の記録フォーマット

プリフライトチェックの結果は `task.md` に記録する：

```markdown
## プリフライトチェック結果

| チェック | 結果 | 備考 |
|---|---|---|
| 型チェック | ✅ PASS | |
| Lintチェック | ✅ PASS | |
| ユニットテスト | ✅ PASS | 42件すべて通過 |
| ビルド | ✅ PASS | |
| glm-46e レビュー | ✅ OK | 軽微なコメント1件（記録済み） |
| glm-46f セキュリティ | ✅ 問題なし | |

→ PR作成可能
```

---

## 判定基準

| 状態 | 対応 |
|---|---|
| 全チェック PASS | 次のステップへ進む |
| WARNING あり | 内容を記録してユーザーに共有。軽微なら続行可 |
| CRITICAL / HIGH リスクあり | **必ず修正してから再チェック。スキップ禁止** |
| チェックツールが使えない | ユーザーに手動確認を依頼する |

## 問題発見時のISSUE登録

チェック中に発見した問題は**必ずISSUEに登録する**。口頭共有や `task.md` へのメモだけで終わらせない。

### どのような問題をISSUEにするか

| 問題の種類 | ISSUEを作る？ |
|---|---|
| 今すぐ修正できるバグ（数行） | 修正してからISSUEをクローズ済みで作成（記録として残す） |
| 修正に時間がかかるバグ | ISSUEを作成して作業中のPRとリンク |
| 今回のスコープ外の問題 | ISSUEを作成してラベル `backlog` を付ける |
| セキュリティリスク（MEDIUM以上） | ISSUEを作成してラベル `security` を付ける（非公開にすることも検討） |
| 軽微な改善提案（INFO） | 任意。積み上がったらISSUEにまとめる |

### ISSUEに含める情報

```markdown
## 概要
<何が問題か1行で>

## 発見箇所
- ファイル: src/xxx.ts:42
- 発見タイミング: PRレビュー / セキュリティスキャン（glm-46f）/ テスト実行

## 詳細
<エラーメッセージ・再現手順・問題の説明>

## 影響範囲
<どこに・誰に影響するか>

## 対応案
<修正方針または調査方針>
```

### ISSUEラベルの使い分け

| ラベル | 用途 |
|---|---|
| `bug` | 明確なバグ・誤動作 |
| `security` | セキュリティリスク |
| `technical-debt` | 今は動くが将来問題になりうる設計 |
| `backlog` | 今回対応しないが記録しておく問題 |
| `glm-generated` | GLM生成コードに起因する問題 |

### ISSUEの作成方法

`github.md` のワークフローを参照：`.agents/workflows/github.md`

```
mcp__github-mcp-server__create_issue
  - title: "fix: ○○でNullPointerExceptionが発生する"
  - body: 上記テンプレートに従って記述
  - labels: ["bug"] など
```

**原則: 発見した問題は流さない。ISSUEで追跡可能にする。**
