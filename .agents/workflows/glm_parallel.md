# GLM 並列処理ワークフロー

## 前提

- Leadエージェント（Antigravity）がこのワークフローを実行する
- GLMはステートレス。呼び出しのたびに必要なコンテキストを渡す
- 依存関係のないタスクは必ず並列で呼び出す

---

## パターン1: 実装とテストの並列生成

```
[並列呼び出し]
  glm-46  ← 「○○を実装せよ」+ 既存コードのコンテキスト
  glm-46b ← 「○○のテストを生成せよ」+ 仕様・型定義のコンテキスト

[Lead]
  両方の結果を受け取り → レビュー → ファイルに書き込む → テスト実行
```

## パターン2: 複数ファイルの並列実装

```
[並列呼び出し]
  glm-46  ← ファイルAの実装
  glm-46c ← ファイルBの実装（独立している場合）

[Lead]
  両方の結果を統合 → 整合性を確認 → 書き込む
```

## パターン3: 実装・テスト・レビューの完全並列（独立タスク向け）

```
[並列呼び出し]
  glm-46    ← 新機能の実装
  glm-46b   ← 既存機能の追加テスト
  glm-46c ← 別ファイルのリファクタ案

[Lead]
  各結果を独立して適用
```

## GLMへの指示テンプレート

### 実装依頼（glm-46 / glm-46c）

```
あなたはシニアTypeScriptエンジニアです。

【規約】
- any禁止、明示的な型定義を使う
- ネストは浅く、早期リターンを使う
- 未使用コード・コメントアウトは削除する
- テストなしのコードは出さない

【コンテキスト】
<関連ファイルの内容・型定義をここに貼る>

【タスク】
<具体的な実装指示>

出力はコードのみ。説明は不要。
```

### テスト依頼（glm-46b）

```
あなたはシニアTypeScriptエンジニアです。

【規約】
- Jest + React Testing Library を使う
- モックは最小限にする
- 正常系・異常系・エッジケースをカバーする

【コンテキスト】
<テスト対象のコード・型定義をここに貼る>

【タスク】
<テストケースの要件>

出力はテストコードのみ。説明は不要。
```

### レビュー依頼（glm-46c）

```
あなたはシニアTypeScriptエンジニアです。

以下のコードをレビューしてください。

確認観点：
1. バグ・ロジックエラー
2. 型安全性（anyの使用など）
3. パフォーマンス上の問題
4. セキュリティリスク（インジェクション・XSS等）
5. 改善できる点

【コード】
<レビュー対象コードをここに貼る>

問題点と改善案を箇条書きで出力してください。
```

## エラー処理

GLMがエラーを返した場合：

1. エラーメッセージをそのまま確認する（握りつぶさない）
2. コンテキスト不足なら → 必要な情報を追加して再呼び出し
3. GLMが仕様を誤解している場合 → Instructionをより具体的に書き直す
4. 3回試みても解決しない場合 → Leadエージェントが直接実装する

---

## バッチ処理（30件以上）

1. 方針決定 → `glm-46c` でレビュー → フィードバック反映
2. batch1（最初の数件）のみ実行 → 品質確認（QC）
3. QC NG → **全処理停止** → 根本原因分析 → 方針修正 → 2に戻る
4. QC OK → batch2以降を実行
5. 全バッチ完了 → 最終QC

**batch1のQCを絶対にスキップしない。**
