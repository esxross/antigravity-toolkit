# GLM 並列処理ワークフロー

## 前提

- Leadエージェント（Antigravity）がこのワークフローを実行する
- GLMはステートレス。呼び出しのたびに必要なコンテキストを渡す
- 依存関係のないタスクは必ず並列で呼び出す

---

## パターン1: 実装とテストの並列生成

```
[並列呼び出し]
  glm-46  ← 「○○を実装せよ」+ 既存コードのコンテキスト
  glm-46b ← 「○○のテストを生成せよ」+ 仕様・型定義のコンテキスト

[Lead]
  両方の結果を受け取り → レビュー → ファイルに書き込む → テスト実行
```

## パターン2: 複数ファイルの並列実装

```
[並列呼び出し]
  glm-46  ← ファイルAの実装
  glm-46c ← ファイルBの実装（独立している場合）

[Lead]
  両方の結果を統合 → 整合性を確認 → 書き込む
```

## パターン3: 実装・テスト・レビューの完全並列（独立タスク向け）

```
[並列呼び出し]
  glm-46    ← 新機能の実装
  glm-46b   ← 既存機能の追加テスト
  glm-46c ← 別ファイルのリファクタ案

[Lead]
  各結果を独立して適用
```

## パターン4: Git Worktree + GLM並列（ファイル競合ゼロ）

**対象**: 複数機能を同時開発 / 同一ファイルへの書き込みが競合しうるケース

```
[Lead] 事前準備：API境界・型定義・インターフェースを先に確定する

[Lead] worktreeを機能ごとに作成
  git worktree add ../worktree-feat-a feat/feature-a
  git worktree add ../worktree-feat-b feat/feature-b

[並列呼び出し]
  glm-46  ← feature-a の実装（../worktree-feat-a/ 向け）
  glm-46b ← feature-b の実装（../worktree-feat-b/ 向け）

[Lead]
  各worktreeに結果を書き込む → 独立してテスト実行
  完了後 → PR作成 → マージ → worktree削除
  git worktree remove ../worktree-feat-a
  git worktree remove ../worktree-feat-b
```

### 注意事項

- **同一ファイルへの同時書き込みは禁止**: マージコンフリクトが発生する
- **共有リソースに注意**: DB・Dockerデーモン・キャッシュはworktree間で共有されるため、DBステートの同時変更でレースコンディションが発生しうる
- **型定義・API境界は先に合意する**: worktree分割前に `types.ts` や API インターフェースを確定しておく

### glm-46 — テスト生成A（正常系・仕様ベース）🔴 RED

```

仕様から「正常系」のテストを生成してください。

- まだ実装は存在しないので、テストは必ず失敗する状態で出力する

【規約】
- Jest + React Testing Library を使う
- describe/it でテストを構造化する
- テスト名は日本語でも可（何をテストしているか明確に）
- モックは最小限にする

【コンテキスト】
<仕様・型定義・インターフェース定義をここに貼る>

【タスク】

出力はテストコードのみ。説明は不要。
```

### glm-46e — Critic（批評・改善提案）🔵 REFACTOR

```
あなたはシニアTypeScriptエンジニアです。TDDのREFACTORフェーズを担当します。

【役割】
テストコードと実装コードを批評し、改善案を提示してください。

確認観点：
1. テストの網羅性（カバーされていないケースはないか）
2. テストの保守性（テストが脆くないか・変更に弱くないか）
3. 実装のロジックエラー・バグ
4. 型安全性（anyの使用・型推論の漏れ）
5. パフォーマンス上の問題
6. コードの可読性・保守性
7. 設計上の問題（責務の分離・依存関係）

【テストコード】
<glm-46 + glm-46b の出力をここに貼る>

【実装コード】
<Leadが採用した実装（glm-46c or glm-46d）をここに貼る>

問題点と改善案を箇条書きで出力してください。
```

### glm-46f — セキュリティ・品質レビュー（全フェーズ）

```
あなたはシニアセキュリティエンジニアです。全フェーズを通じてセキュリティと品質を監査します。

【役割】
コードのセキュリティリスクと品質問題を検出してください。

確認観点：

5. 機密データの不適切な露出（ログ出力・エラーメッセージ）
6. 依存ライブラリの既知脆弱性

【コード】
<レビュー対象コード（テスト・実装）をここに貼る>

セキュリティリスクを深刻度（HIGH/MEDIUM/LOW）付きで箇条書きで出力してください。
問題がない場合は「問題なし」と出力してください。
```

---

## エラー処理

GLMがエラーを返した場合：

1. エラーメッセージをそのまま確認する（握りつぶさない）
2. コンテキスト不足なら → 必要な情報を追加して再呼び出し
3. GLMが仕様を誤解している場合 → Instructionをより具体的に書き直す
4. 3回試みても解決しない場合 → Leadエージェントが直接実装する

---

## バッチ処理（30件以上）

1. 方針決定 → `glm-46c` でレビュー → フィードバック反映
2. batch1（最初の数件）のみ実行 → 品質確認（QC）
3. QC NG → **全処理停止** → 根本原因分析 → 方針修正 → 2に戻る
4. QC OK → batch2以降を実行
5. 全バッチ完了 → 最終QC

**batch1のQCを絶対にスキップしない。**
